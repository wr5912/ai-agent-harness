## When-to-use

在 `threat-analysis-hypothesis-falsification` 已完成立靶并生成具体场景、且 `get_threat_event` 已返回事件实体与时间窗后使用。

立靶已经截断时不要继续取证。本 skill 的输出交给证伪引擎，用于：

- 核对规则主张是否与事实一致；
- 判断各具体场景的必要前提和因果联系是否成立；
- 将事件真假与攻击进展分离。

---

## Workflow

### 步骤 1 — 确定取证边界

取证边界由归一实体和放宽后的时间范围共同构成，不等同于规则窗口：

- 实体使用层 2 已完成的 `resolve_entity` 结果；
- 时间范围在 `firstSeenTime` 和 `lastSeenTime` 两端按场景需要放宽；
- 放宽幅度应由候选场景可能的前置与后续行为决定，并在报告中说明。

事件 `windowSeconds` 是聚合开火窗口，不是攻击持续时间。贴边查询可能漏掉入口、结果或后续动作。

### 步骤 2 — 用已取关联告警建立事实序列

复用层 2 已取得的 `get_alerts(incidentId)` 结果，不重复调用。按 `time` 排序，至少抽取：

| 字段 | 用途 |
|---|---|
| `actor.account` / `actor.sourceIp` | 行为主体 |
| `target.assetId` / `target.ip` | 行为对象 |
| `action` | 实际动作 |
| `outcome.result` | `SUCCESS` / `FAILURE` / `UNKNOWN` |
| `outcome.reason` / `outcome.detail` | 成败原因与返回状态 |
| `attack[].technique` | 检测侧分类主张，只供对照 |
| `alertId` | 证据引用 |

未知或污染的 `outcome.result` 一律归为 `UNKNOWN` 并记入 `data_gaps`，不得猜测成败。

### 步骤 3 — 用日志两跳补齐判据点

告警是稀疏素材，日志用于验证候选场景需要的事实。保留两跳查询：

1. 第一跳 `query_logs` 只取聚合，查看动作、实体和时段分布，不拉大量原文；
2. 第二跳按仍存活场景的必要条件收窄范围，取带 `logId` 的原始记录。

`truncated: true` 必须进入 `data_gaps`，不得把截断结果当全集。工具结果应复用，不因 skill 文本再次提及而重新查询。

### 步骤 4 — 建立场景专属因果路径

**ATT&CK tactics 本身没有固定顺序。** tactic 和 technique 用于描述观察到的行为类别，不是通用状态机，也不天然证明攻击存在。

对每个仍存活的具体场景分别建立最小因果图：

```text
场景 S
  必要前提 P1 --证据/因果--> 行为 A --结果证据--> 结果 R
  必要前提 P2 --证据/因果--/
```

逐项标记：

- `OBSERVED`：有带 ID 的事实证据；
- `CONTRADICTED`：有证据与该必要前提直接矛盾；
- `NOT_OBSERVED`：覆盖完整但没有记录；
- `UNKNOWN`：数据源缺失、查询失败、范围不足或该前提本就不可观测。

只有同时满足以下条件，缺失前提才能排除该具体场景：

1. 它确实是这个场景不可替代的必要前提，而非常见步骤；
2. 对应数据源在相关窗口持续健康且字段可观测；
3. 查询范围正确、结果未截断；
4. 缺失与场景主张构成直接矛盾。

同一条证据可以影响多个场景，但必须逐场景解释。某场景的必要前提不成立，不能自动排除其他具有不同入口、路径或目标的恶意场景。

### 步骤 5 — 将 ATT&CK 分类与事实证据分开

告警自带 ATT&CK 标签属于检测侧主张，不能反过来独立支持 H1。只有已由 `alertId` 或 `logId` 确认的事实动作，才可以附加 tactic/technique 分类；无法可靠映射时保留事实描述，不强行分类。

不要检查“某 tactic 是否排在另一 tactic 前面”，而要检查“这个具体场景声称的因果关系是否得到事实支持”。多阶段、单阶段、并行、重复或从已失陷节点开始的行为都应按自己的证据路径还原。

### 步骤 6 — 判定进展而非替代事件结论

输出：

1. `timeline`：每个事实动作及其证据 ID；
2. `scenario_paths`：每个具体场景的必要前提、因果边与状态；
3. `response_context.attack.progressed` 候选值：`SUCCEEDED` / `ATTEMPTED` / `UNKNOWN`；
4. `data_gaps`：盲区、截断和不可观测项。

进展只能依据行为与结果证据：明确目标已达成为 `SUCCEEDED`；确认恶意行为但结果失败为 `ATTEMPTED`；无法判断结果为 `UNKNOWN`。进展不直接决定 `verdict`。

## Verification

本次执行只有在以下条件全部满足时有效：

| # | 检查项 | 验证方式 |
|---|---|---|
| 1 | 取证范围覆盖场景前后文 | 时间窗两端已按场景放宽，理由明确 |
| 2 | 时间线事实均有引用 | 每个动作都能追溯到 `alertId` 或 `logId` |
| 3 | 日志查询保留两跳 | 第一跳聚合、第二跳只取场景判据点原文 |
| 4 | 每条路径属于具体场景 | 未使用一条固定 ATT&CK 阶段序列套所有场景 |
| 5 | 缺失前提经过覆盖校验 | 排除场景前已验证必要性、采集健康、范围和截断状态 |
| 6 | ATT&CK 只作分类 | 没有用告警标签证明事件为攻击，也没有依赖 tactic 顺序 |
| 7 | 进展来自结果证据 | `SUCCEEDED` / `ATTEMPTED` / `UNKNOWN` 可追到具体记录 |
| 8 | 盲区未被当成矛盾 | `ERROR`、不健康采集和不可观测项均进入 `data_gaps` |

---

## ATT&CK 覆盖

本 skill 可为任意已观察行为附加 ATT&CK 分类。覆盖度表示“哪些行为有事实证据”，不表示必须经历哪些 tactic，也不表示 tactic 之间存在统一顺序。
