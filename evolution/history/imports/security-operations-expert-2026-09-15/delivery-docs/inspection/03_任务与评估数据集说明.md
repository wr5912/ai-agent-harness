## 3. Eval Case 契约

- 字段：`id`、`requirement_ids`、`scenario_id`、`intent_id`、`tags`、`source_type`、`variant_types`、`input`、`context`、`expected_behavior`、`check`、`gate`

- 项目自定义 `context` 字段：`quality_review`、`baseline_commit`，以及执行某个 Case 所需的目录可用性、服务返回、身份、覆盖率、事实、错误或注入条件。
- ID 规则：`case-ins-NNN`、`REQ-INS-NNN`、`SCN-INS-NNN`、`INT-INS-NNN`。
- 当前 50 条 Case 均采用可确定性判定的 `blocking` 门禁；没有 `scored` Case。

## 4. Trial 与聚合规则（运行前冻结）

- 每个 Case 的 Trial 次数：1；模型或环境出现明显随机性时，须在新 Baseline 中提高次数并重新冻结。
- `blocking` Case：任一 Trial 失败即失败；全部要求的 Trial 通过才通过。
- `scored` Case 聚合规则：`N/A`，当前无 `scored` Case。
- 证据最低要求：最终回复；按序 Tool 调用及参数；`run_id`/`next_action`；身份与租户来源；服务端结果；对写操作和报告访问场景还需真实最终状态或拒绝证据。
- 当前 Trial 状态：应执行 50，实际执行 0；`results.csv` 仅保留规范表头，不创建虚假状态行。

### 建议的同事复核动作

1. 逐条确认输入是否符合真实用法、是否与其他输入存在实质差异。
2. 确认预期行为和检查项可由现有测试 Harness 观察，不可观察的条目退回修改。
3. 把真实失败或用户反馈补成 `regression` Case，并记录来源编号。
4. 记录复核人、依据、日期、剔除数和剔除原因；若有效 Case 或不同 Input 少于 50，补充高质量条目后生成新 Eval Set 版本及哈希。
