# 页面覆盖与关键边界

本参考用于梳理**基于 DSH 的未来智能体运行平台**。使用前先核对目标仓库、DSH 锁定版本和用户最新要求；页面名称与数量可以随产品范围调整，不把某份历史清单的 112 项任务或本机路径当作固定合同。

在当前 `ai-agent-harness` 仓库，优先从 `AGENTS.md`、`docs/standards/SOURCES.md`、`docs/standards/PROJECT-INTERPRETATION.md`、`docs/ai-agent-harness项目验收矩阵.md`、`runtime/adapters/dsh-container/source.lock.json`、`docs/DSH智能体运行管理平台设计方案.md` 和 `docs/智能体多形态Harness资产模型设计方案.md` 取证；现有任务清单通过文件搜索定位，不假设旧文件名仍在。换仓库时重新寻找对应来源。

建设顺序可用阶段标记表达，但阶段不是当前实现状态：`G1a` 为单 Agent、单操作者的实例—业务对话—Trace 闭环；`G1b` 增加 Harness 改进、Hub、评测、发布和变体；`G2` 承接长期业务用户、身份隔离、启用与回退；`G3` 只在工作量或收益有实测依据后考虑自动选版、自动候选和扩容。用户另定里程碑时以其定义为准。

## 页面旅程

| 页面 | 用户要完成的事 | 任务梳理时容易漏掉的工作 |
| --- | --- | --- |
| 智能体首页与 Harness 资产 | 找到 Agent、看来源和实际状态、进入编辑与比较 | 可编辑 Candidate、Git 差异、已发布版和实例装载快照各有身份；页面不维护第二份资产正文 |
| 管理智能体对话 | 用对话新建、修改、配置、诊断、评估和优化 Agent | 专用管理 DSH；精确目标、多轮上下文、预览、确认、持久操作回执；与 GUI 共用确定性服务 |
| MCP、Skill、Plugin、知识库 Hub | 查找、登记、绑定、验证和维护能力 | 四类来源与生命周期各自明确；MCP 工具编排组合并发布新工具；Plugin 的安装、启停和卸载不等于登记 |
| 算力变体 | 从已发布父版派生更省资源、效果近似的 Harness | 同 Agent `published` 且可恢复的 HarnessVersion；独立 Candidate、共同 Case、质量与资源双门槛、真实 Run、人工 Decision |
| DSH 实例 | 创建、观察、启停和恢复容器 | 精确资产快照与标准镜像、只读 Harness、独立 HOME、期望与实际状态、真实 Session 探针 |
| 业务对话与定时任务 | 真实多轮提问、流式查看、取消、找回历史和定时执行 | 模型与工具执行证据、断线恢复、Session 与版本/实例固定关联；管理对话另存 |
| 执行追踪 | 从一次回答定位模型、工具、失败和用量 | DSH 原始事件与平台索引、持久采集与缺口显示；组合 MCP 的父调用与子步骤可靠关联 |
| 反馈与问题 | 评价精确回答，形成改进线索 | 反馈归属 message/Session/Invocation；从问题到 Case 须人工核对，旧回答不自动成为标准答案 |
| 测试集与实验 | 固定测试口径、运行真实 Agent、逐例比较 | 唯一可编辑测试来源、独立 Run、环境可比性、原始证据、退步与不确定结果 |
| HarnessVersion 发布、启用与回退 | 封存可恢复版本，决定新会话使用哪个版本 | `published`、可手选、默认路由分开；预检和真实任务探针；旧 Session/定时任务不悄悄迁移 |
| 用户设置与运维 | 看真实配置、故障、备份恢复和用户归属 | 多用户能力按需建设；DSH Web Token 不等于业务用户身份；实例数据、Trace、Run 分开处理 |

## 必须分清的状态和事实源

- `Candidate` 是可编辑的 Experiment 工作树；`Run` 是一次执行的原始记录；`Research Release` 是研究归档。平台的 `HarnessVersion` 是另行显式发布、不可变且可恢复的 Agent Harness；`Deployment` 管新业务会话路由；`Instance` 是实际 DSH 容器。研究 `adopt`、发布和业务启用是三个动作。
- 平台算力变体只以**同一 Agent 已发布且可恢复的 HarnessVersion**为父版。Git HEAD、Research Release、尚在编辑的 Candidate 和正在运行的实例都不能替代。未业务启用的已发布版仍可派生；变体通过研究比较后还需另行发布，发布也不自动接业务流量。
- “效果几乎等价”在试验前写定适用任务、Case、评审口径、最低质量、关键 Case 退步红线、相对父版差额和资源目标；所有必要门槛同时满足才可标记达标。`no-compute` 须说明本地、远端和工具内部的推理及 embedding。资源和效果都从真实 Run 取证。
- 同一业务 Agent 的新实例复用当前标准 DSH Runtime 镜像；Harness 和 Plugin 的易变资产尽量经只读快照装载，不为每个变体造派生镜像。要精确复现历史父版时按其清单锁定镜像；换新 Runtime 做比较须标明迁移并重新验证。
- 按锁定 DSH 版本核对：`Profile` 怎样组合启动扩展，`Preset` 怎样决定 Session 配置，实际模型又在哪里选择和运行；配置文件写好、实例装载与模型或工具真实调用分层展示。
- Hub 卡片要分开显示登记、绑定、实例装载、实际调用和评测受益。先核对锁定 DSH 的 MCP 客户端、Plugin Manager 与 `inspect` 的确切范围；这些原生入口或一次连接成功，不自动构成跨 Agent 的 Hub、业务可用性或发布能力。若 `inspect` 仅给包元数据，完整代码和依赖清点需平台另取确定包内容。Plugin 操作先落候选资产，在隔离可写 Profile 验证，再用新快照核验。
- LangSmith 等产品可用来比较 Trace 树、数据集、逐例评估与反馈体验；它们的界面不能作为 DSH 已实现相同能力的证据。
- Trace 的实时流片段不等于完整记录；跨容器事件须保存、对账并显示缺口。容器 Running、HTTP `200`、MCP 握手、工具目录可见和异步操作“已受理”都不等于任务成功。反馈、Trace、Session、Invocation、研究 Run 各有独立身份与来源。
- 长期业务服务时，业务版本回退只改变**后续新 Session**；旧 Session 固定旧版和原实例。定时任务、在途任务、已发生副作用须单独说明。多用户身份由平台服务端核验，隔离要覆盖 Session、附件、Schedule、Trace、Hub 和管理工具入口。

## MCP 工具编排组合

把多个细粒度 MCP 工具按有界流程组合成面向一个步骤或子任务的新工具，作为 MCP Hub 的一项用户可见能力，不把它误写成“把工具一次性交给模型”。至少覆盖：

1. 在 Hub 选择确切下游服务与原子工具，画顺序和必要的条件分支，映射输入输出，并定义新工具的 `inputSchema`、`outputSchema`；下游输出无结构化字段时，先定义并试验文本提取规则。
2. 用受控来源保存唯一可编辑流程草稿，逐步试跑并展示失败、超时、已发生的副作用和未执行步骤。默认确定性执行，不在节点之间无故重复请求模型。
3. 由平台新建执行器和 MCP 服务，把组合版经 `tools/list`、`tools/call` 发布为新工具；固定版本对应的服务端点与工具名，以及下游服务实现的可验证来源/版本和工具字段指纹，不让旧映射静默指向新版。Agent Candidate 固定 DSH 实际连接的版本化端点和工具身份；无法固定的外部实现需标复现限制并重验。
4. 每个子调用沿原调用者权限边界执行，凭据由对应连接提供；父子调用 ID、组合版本和下游步骤进入 Trace。若锁定 DSH 未传父调用标识，需要平台桥接或最小客户端扩展，无法关联时显示未知。
5. 在相同任务、模型和环境下，对比逐个调用与组合调用的正确率、模型推理轮次与 Token、下游调用次数、端到端耗时、费用和失败率。一次 Agent 层工具选择仍可能包含多次下游 MCP 调用，收益是待验证目标。

发布组合 MCP 工具和发布 Agent 的 HarnessVersion 不同；Agent 发布版的清单还要固定组合流程、执行器及下游依赖的可验证身份。每次使用前核对目标 MCP 规范版本：若标准没有单工具版本或编排引擎，就把版本映射和执行能力明确列为平台新增工作，不能称为 DSH 原生能力。
