# Harness 工程平台任务清单

把“从 DSH 出发建设 Harness 工程平台”写成产品负责人能从熟悉的界面理解、研发团队能据此拆解的 Markdown 任务清单。读者可以熟悉 Agent 平台，但不应被要求理解后端实现才能拼出一个功能。此 Skill 只处理任务梳理和文档修订；用户另行要求开发时，按当次授权处理。

## 先核实起点

1. 读取目标仓库的 `AGENTS.md`、规范解释、项目验收矩阵、DSH 来源锁与平台方案；检查工作树和现有任务清单。找不到某项来源就标缺口，不从旧文档或 Memory 推定现状。修订现有清单时保留用户已改的文字和稳定任务 ID，精准加入新要求。
2. 对“是否已从工具阶段具备转入平台开发的条件”先给有证据的阶段判断和缺口；即使尚未就绪，也可梳理未来任务，但不能写成已获实施授权。区分**已实现并验证、已有代码但未完成行为验证、未来平台待开发、外部产品参考**。当前 `ai-agent-harness` 若仍是 Research Mode，平台任务应明确写作未来方案，不把研究 CLI、技术探针或 Research Release 称作生产平台能力。
3. 需要说明 DSH、MCP、LangSmith 等可变实现或标准时，核对目标版本的源码和官方资料；引用直接支持论断的来源。原型、端口、HTTP `200`、握手、工具登记与真实业务效果各自只能证明对应的一层。

## 从页面组织任务

先写一次用户能走通的界面旅程，再列页面导航与建设顺序。按 [页面覆盖与关键边界](references/page-coverage.md)检查能力范围；它是覆盖提示，不规定任务总数或固定技术架构。

默认交付为**一章产品总览 + 页面章节**。每个页面的任务表只用 `任务名称｜任务描述｜任务内容` 三列：

- **任务名称**：一项用户可感知、能独立核对结果的能力，必要时加稳定 ID 和建设阶段。
- **任务描述**：用非开发人员能理解的话说明用户得到什么、为什么需要它；把论述理由写在这里，独特的事实依据可在页面引言或相邻文字给出链接。
- **任务内容**：用 `①②③…` 列完成这项能力必需的界面、确定性服务、DSH/AI 接入、数据和真实验证子任务。只写相关部分，不机械要求每项都覆盖所有层。

把同一个用户动作的选择、预览、确认、状态和失败处理合成一项主任务；较大的任务在内容列分子任务。不同的业务决定要分开，例如修改与评估、发布 HarnessVersion 与启用业务流量。不要为每个按钮、字段、接口或错误分支另起一行，也不要增加“单项研发交付”“论述依据”列或与逐页任务无关的章节。

管理智能体对话与 GUI 页面应调用同一组受控服务、显示同一操作回执；管理会话与业务会话分开。四类 Hub、DSH 实例、对话、Trace、反馈、评估、发布和运维的前后端工作都应落在相应页面任务中。尤其检查 MCP 工具**编排组合并发布为新 MCP 工具**、Plugin Hub 管理，以及从同一 Agent 可恢复的主线版本派生不同算力的等效 `end` 变体；研究阶段推荐已发布父版，但不强制，该终端变体不要求后续主线版本继承。

## 校核与交付

- 按 [页面覆盖与关键边界](references/page-coverage.md)核对对象状态、来源、发布与启用、单镜像、真实装载、父子 Trace 和效果证据；避免跨页重复建设同一服务，并让引用指向负责该服务的任务。
- 核对章节、三列表格、任务 ID 与交叉引用、文档链接和敏感信息；对修改后的文档逐项检查“任务名称能否独立理解、描述是否说清原因、内容是否可执行”。对效率或质量改善只写测量方法，不把目标当成已发生结果。
- 写入用户指定路径；修订时优先更新现有文件，不另造内容重叠的清单。新建且未指定目录时，优先写入用户可访问的 `~/Downloads`，不可用时写 `/tmp`，使用不覆盖已有文件的名称。最终说明文件路径、实际修改、已做的文档检查及未执行的运行验证。未经要求不实现、启动、提交或发布平台。
