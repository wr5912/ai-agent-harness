# 总监可读的任务文档

把零散任务写成便于决定先做什么、为什么做、怎样判断完成的 Markdown。保留技术事实，但用业务结果解释任务，不要求读者先懂仓库结构或实现细节。

## 取材与范围

- 以用户本次要求和指定材料为范围。涉及本项目现状或阶段判断时，核对根级 `AGENTS.md`、`docs/standards/PROJECT-INTERPRETATION.md`、`docs/ai-agent-harness项目验收矩阵.md` 及任务直接相关的原始资料。旧报告与 Memory 只作线索；记录核对日期或版本。
- 用户指定已有文档时直接更新该文档，保留仍有效的任务、编号、链接和人工补充；新建文档时优先使用用户指定路径，否则放在 `docs/`。同一批任务只维护一份可编辑清单。
- 合并重复描述可以，不能无说明遗漏、改变任务范围，或把未来设想写成当前已完成的能力。材料不足时写明待确认内容及其影响，不编造负责人、期限、成本或进度。

## 写法

- 开头用几句话直接回答当前要做什么、最先处理什么、哪些条件影响推进。按读者要作的决定组织内容，不按代码目录罗列。
- 每项任务用直接的中文说明要解决的问题、预期结果和可观察的完成标志；需要排序时说明依赖和阻塞。首次出现的专有名词给出简短解释，稳定编号、产品名和必要来源路径保持准确。
- 用户要求优先级时，给每项标注并说明分级依据；把“优先做”和“阶段切换前必须完成”分别标注。条件触发的任务写清触发条件，缺少判断依据时标为待确认，不制造精确排序。
- 已验证的现状、尚未验证的判断、拟开展的任务分别表述。关键结论链接到事实来源；技术检查、页面可打开或原型存在，不等于业务效果已得到证明。
- 使用简短段落和必要的索引表；避免逐项堆砌实现术语、空泛收益、固定模板或重复的项目规则。

## 交付检查

核对任务覆盖、编号、数量、优先级与依赖是否一致，链接是否可用，限制是否明确；不在文档中写入凭据。只创建或编辑本次要求的 Markdown，引用原有事实来源；不顺带执行清单里的开发任务，也不把文档完成写成任务完成。
