# Harness 引导式工作流

把复杂任务拆成少量可确认的对话轮次。每轮只解决一个决策，使用仓库现有文件记录最终事实，不为流程另建状态、阶段目录或检查表。

流程借鉴 GSD 的阶段式交互：先讨论上下文，再形成可执行计划，随后实施并验证；只采用这种对话节奏，不复制额外状态目录或工作流框架。

## 开始前

1. 阅读根级 `AGENTS.md`、`docs/standards/SOURCES.md`、`docs/standards/PROJECT-INTERPRETATION.md` 和项目验收矩阵。
2. 检查 Git 工作树和目标资产，保留已有改动。
3. 先判断任务类型：`新建`、`迁移`、`修改` 或 `优化`。信息不足时用一个简短问题确认，不一次抛出整份问卷。
4. 明确本次涉及的 `PA-xx`、允许修改的对象，以及需要观察的 DSH 行为。

## 多轮 SOP

### 1. 讨论

依次确认：

- 要解决的真实问题和目标用户；
- 目标 Agent、现有 Baseline 或待迁移来源；
- 成功时可观察到的行为，以及不能回归的行为；
- 工具、数据、模型、运行环境和副作用边界；
- 本轮不做什么。

每轮复述已确认事实、仍未知内容和当前建议。可以从一个高价值场景开始，不要求用户预先掌握 Harness 术语。

迁移任务在讨论阶段调用 `$legacy-asset-intake`，先只读清点来源；不得执行来源内脚本、Hook、Plugin、Skill 或 Workflow。

### 2. 计划

信息足以动手后，给出最小执行计划，至少包含：

- Baseline 引用；
- 一个可证伪的研究假设；
- Candidate 的精确修改范围；
- 最小但有区分力的 Evaluation，以及必要反例或回归；
- 预期修改文件、验证命令、停止条件和未覆盖边界。

新建、修改、优化和经确认的迁移都调用 `$harness-evolution` 建立或继续一个 Experiment。计划获得用户确认前，不写入 Harness 资产；用户已经给出明确实施方案或直接要求实施时，可将其视为确认并继续。

### 3. 执行

只实施已确认范围：

- 目标 Harness 源码写入当前 Experiment 的 `candidate/`；
- 同一研究口径的需求、任务、测试数据、方法和验收只保留一个可编辑事实源；
- 优先复用 DSH 现有 Runtime、Preset、Plugin、MCP 和 Skill；
- 源码写入后用新进程或新 Session 核对实际装载，不把容器副本当作唯一来源；
- 发现前提错误、范围扩大或需要新授权时，暂停执行并回到讨论轮次。

不得自动提交、推送、发布、删除或运行不可信资产。不得把上游生产规范的审批、固定 Case、R1/R2/R3 或发布门禁自动引入 Research Mode。

### 4. 验证与决策

调用 `$research-eval` 执行或检查已计划的比较，分开报告：

- 项目与工具链验证；
- Experiment 的实际观察、回归、失败和未知状态；
- Research Release 复现（仅在本次确实创建时）。

根据证据记录 `adopt`、`continue`、`reject` 或 `inconclusive`。文件存在、静态校验、容器启动或 HTTP 成功只证明对应局部状态，不代替 Harness 行为结论。

## 四类任务的最小入口

- `新建`：确认首个高价值场景，以 `none:first-experiment` 建立最小 Candidate。
- `迁移`：先只读清点，再明确保留、改写和舍弃项；迁移后按新 Experiment 验证 DSH 行为。
- `修改`：定位当前 Baseline 与具体缺口，只改直接相关资产并补受影响回归。
- `优化`：先用失败样本或观察形成假设；没有可比较证据时，不把主观改写声明为优化成功。

## 对话要求

- 使用新手能理解的中文解释术语，命令和稳定 ID 保持原文。
- 一次最多提出三个紧密相关的问题；能从仓库或运行环境确认的内容先自行核对。
- 每一轮都给出可继续的默认建议，但不替用户作会扩大范围或产生外部影响的决定。
- 完成时列出改动、证据、未验证项和下一步；不把研究结果描述为生产发布批准。
