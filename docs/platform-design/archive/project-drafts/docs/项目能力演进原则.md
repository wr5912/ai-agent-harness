# 项目能力演进原则

> **适用边界**：本文件维护项目长期 R0–R5 能力演进的统一阶段定义。具体开发操作继续服从根级 `AGENTS.md` 的 Research Mode；当前工具链完成状态仍以现有项目验收矩阵为准。

## 定位

`ai-agent-harness` 当前是个人、DSH-only 的 Harness 研究与资产管理仓库。长期愿景是把已证明有效的 Harness 创建、受控优化、测试评估、算力变体、资产版本化与 DSH 实例运行能力，逐步沉淀为可复用的自用工具，并在确有需求时继续成长为 **AI 原生智能体运行管理平台**。

**任务目标、评估数据、验收证据是长期可承接的工程资产；框架与 Harness 实现可以变化。当前仍坚持 DSH-only，不为未来假定的多 Runtime 提前建抽象。研究是能力成熟阶段，不是平台未来永久依赖的一个外部“研究系统”。** 当前 Git 及文件既承载研究资产，也可以在未来继续担任平台内部资产版本化后端；具体仓库、模块、进程、数据库的组织方式以当时的真实维护成本决定，不提前固定。

## R0–R5 阶段路线

| 标签 | 能力重点 | 可以交付的最小成果 | 不意味着 |
|---|---|---|---|
| **R0 研究验证** | 来源锁定、Candidate、真实 DSH 评测、Run、Decision，验证 Harness 工程假设 | 一个可核查且可复验的研究闭环 | 当前所有研究假设已成立 |
| **R1 自用工具** | 从反复的手工步骤中抽出真正有收益的 CLI/Skill 工具 | 一条经反复使用、能减少重复工作的自用路径 | 必须同时有 TUI/Web/数据库 |
| **R2 数据体系** | 明确事实所有权、稳定 ID、存储位置、历史引用、备份恢复 | 从 Run 找到来源/实例/Session，恢复后不串源 | 必须引入 PostgreSQL |
| **R3 工具闭环** | 反馈/失败 → Case 提案 → 人工确认 → Experiment → 评测 → Decision | 一条跨工具、真实可复验且有收益的闭环 | 自动写采用结论或自动发布 |
| **R4 平台构建** | 在同一确定性业务能力上按需建立 Service/API、GUI、LUI/Meta-Harness | 一条真实端到端前后端业务竖切片 | 11 张草图必须同时交付 |
| **R5 持续演进** | 按用户需求与收益扩充 MCP 组合、发布与路由、多人、变体运营等能力 | 一条通过实际协议和用户验收的增量产品能力 | 默认启用多租户、自动路由或微服务 |

这是**能力演进顺序**，不是固定瀑布工期、全局强制审批门禁或所有功能的完成度评分。既有 `dsh-dev` / `dsh-eval` 具有自用工具属性，并不意味着本仓库当前工作模式已经从 Research Mode 转到“平台建设”。某阶段允许交叉、回退、暂停，甚至长期不继续。

## 当前工作边界（Research Mode 不变）

1. **当前工作必须来自真实研究假设、实际重复痛点和授权范围**。未来平台草图及 `G1a/G1b/G2/G3` 任务清单是目标产品需求，不构成批量开工指令。
2. **沿现有资产与工具最小演进**。优先复用 `harness-guided-workflow`、`dsh-dev`、`dsh-eval`、原有 Experiment/Run 与 DSH 原生机制；不要仅因未来可能平台化而新建通用 Service、Web、数据库或队列。
3. **同一事实只有一个可编辑权威**。当前业务 Case 由现有 `evaluation.md` 维护，Candidate/Decision 由 Experiment 维护，Run 封存后不改写，DSH Session 按实例自己的原生机制维护。新增读取、摘要或索引不等于获得修改源事实的权利。
4. **装载来源和实际行为必须分开验证**。配置声明、镜像 running、HTTP 200 和工具接通仅证明局部事实；要证明能力改善必须有固定来源/Case/环境和真实 DSH 运行证据。
5. **研究决定不等于产品发布/业务启用**。`adopt` / Research Release 与未来的 HarnessVersion `published`、Deployment `enabled` 是不同事实，不允许自动衔接副作用。
6. **所有新增复杂度都需要消费者和收益证据**。数据库、跨实例 Trace 采集、MCP Gateway、Meta-Harness、前后端与新 Runtime 抽象不因存在于概要架构图中而自动被授权开发。
7. **保持可停、可删、可回退**。无价值或证据不足的扩展可以停止，保留必要研究证据，不用把失败改称成功，也不允许模型自行执行未经授权的破坏性操作。

## 项目任务、验收和来源的关系

- `R0–R5`：本文件唯一维护**项目长期能力阶段含义**；
- 附件 `G1a/G1b/G2/G3`：未来产品需求优先级，**不是**当前阶段标签；
- 现有 `PA-01…PA-11`：当前项目与工具链验收路径、状态及证据，仍在原项目验收矩阵唯一维护；
- Experiment/Run/Decision：某个 Harness 研究假设的证据与结论，仍按既有目录合同保存；
- 上游 `agent-engineering-spec` 使用的生产交付 `R1/R2/R3`：与本文件同名编号但**语义不同**，不得自动继承其生产门禁；
- 设计报告与候选 Backlog：仅作计划材料，不宣称实现或验收完成。

## 引入新技术层的证据条件

- **CLI → Service/API**：有第二个真实消费者或已出现可复现的跨入口逻辑重复，不只是“以后要做网页”。
- **Git/文件 → 平台数据库**：先识别新平台自己拥有的业务事实及真实并发、操作恢复、复杂查询要求；数据库不得成为可编辑 Candidate/Case 的第二写源。
- **原生 Session → 派生索引/平台采集**：先测官方查询/恢复缺口，再决定只读可重建索引；若要求平台独立持久 ACK，则作为明确的新增产品合同单独验收。
- **工具 → GUI/LUI/Meta-Harness**：同源确定性业务服务已能完成真实任务，并有证据显示新交互入口改善了使用成本、准确性或可操作性。
- **研究版本 → 发布/启用**：存在正式业务运行消费者，资产可恢复、装载/行为经真实试验，并明确区分发布、启用和旧会话来源。

以上是**可以研究的触发条件**，不是一旦满足就自动切换项目工作模式。若需从 Research Mode 正式转入平台建设阶段，先获得项目维护者的明确范围决策，并在独立变更中更新根级 `AGENTS.md`、README、当前能力合同与相应验收要求；不通过阶段名字或周数默默改变项目职责。

## 执行和记录

每次从最小真实任务开始，核对当前代码与验收矩阵 → 明确事实源、预期、停止条件 → 优先复用现有工具 → 做最小改动 → 以真实输入与失败分支验证 → 将结果写回原有唯一记录位置。只有真正增加稳定的独立用户路径时，才讨论是否扩充原有 PA 路径；不建立平行阶段打卡台账。
