# DSH 智能体运行平台开发任务梳理

![](/home/admin/Downloads/01_智能体运行平台首页 dashboard.png)

## 1. 产品总览

首入口是**管理智能体对话LUI界面**，平台的界面分为**对话LUI界面**与**传统管理平台GUI界面**。用户可以说“查这个 Agent 为什么答错”“给它加 MCP”“基于已发布版做一个更省资源的变体”“发布新版本”或“重启实例”。管理智能体负责理解目标、说明计划和引用证据；页面与它使用同一组确定性服务，实际文件变化、容器动作、评测和发布都显示可核对的回执。业务 Agent 则运行在各自的 DSH 容器中，为使用者完成任务；管理会话与业务会话分开。[未来平台方案](/home/admin/work/ai-agent-harness/docs/DSH智能体运行管理平台设计方案.md)。

核查基准是仓库锁定的 [DSH 源码与镜像清单](/home/admin/work/ai-agent-harness/runtime/adapters/dsh-container/source.lock.json)。DSH 的 Session、Profile、Preset、MCP、Skill 和当前 Profile 的 Plugin Manager 可作接入点；跨 Agent 的能力 Hub、业务知识库、容器控制、可靠追踪和多人入口属于本清单要开发及实测的能力。[LangSmith Trace](https://docs.langchain.com/langsmith/view-traces) 与 [Context Hub](https://docs.langchain.com/langsmith/use-the-context-hub)只供界面设计参考，不能当作 DSH 已实现的功能。

## 2. 页面：智能体首页与 Harness 资产

这里是平台的对象入口。总监能从卡片分辨“仓库里有这个智能体”“已有可恢复版本”“容器实际在运行”，再进入资产、实例、对话或评测。业务 Harness 的可编辑事实仍保存在 Git 的 Experiment Candidate；页面展示索引和差异，不维护另一份资产正文。

![](/home/admin/Downloads/02_智能体管理.png)

左侧定位智能体，右侧并列查看来源、已发布版本、实际实例、Harness 差异与能力装载状态。

| 任务名称 | 任务描述 | 任务内容 |
| --- | --- | --- |
| AG01 智能体列表与定位（G1a） | 打开首页即可找到要管理的智能体，空仓或来源读取失败也能看懂当前情况；否则后续创建实例和修改资产容易选错目标。 | ① 前端展示名称、用途、Agent ID、来源状态与实际可用实例数，提供名称/ID 检索和明确空态。<br>② 服务端从现有资产登记与实例观察生成列表，区分“未登记、未运行、读取失败”。<br>③ 点击卡片时传递精确 Agent ID，不以相似名称代替身份。 |
| AG02 智能体详情与来源核对（G1a） | 详情页让人知道当前看到的是哪份研究资产、哪份已发布 Harness，以及哪台实例真正装载了它；不能把正在编辑的文件称为发布版。 | ① 展示 Experiment/Git 提交、dirty 状态、已发布版本、实例状态与最近观察时间。<br>② 服务端沿来源清单解析到实际文件摘要、装载快照和容器观察；缺失或过期时明确标出。<br>③ 提供“创建实例”“最近会话/Trace”入口，并在跳转时保持 Agent 和来源身份。 |
| AG03 Harness 文件与差异查看（G1b） | 产品人员可像查看版本文件夹一样看 Prompt、业务 AGENTS.md、Preset、Skill 和 Plugin 的内容及变更，理解一次优化究竟改了什么。 | ① 展示只读文件树、内容、Git 来源和历史版本。<br>② 选择 Baseline 与 Candidate 后逐文件展示差异，并标出未提交修改。<br>③ 缺文件或来源不可恢复时显示真实缺口；页面不复制出第二份可编辑正文。 |
| AG04 Candidate 建立、编辑与检查（G1b） | 用户在一个明确的实验工作区修改 Harness，随时看见真实差异和检查结果，知道文件保存与实例生效是两回事。 | ① 选定 Agent、Experiment 与 Baseline，创建或打开唯一 Candidate，已有内容不覆盖。<br>② 从页面进入限定 Agent 和路径的受控编辑服务或开发会话，直接修改 Prompt、Preset、Skill 等目标资产，不改变开发智能体身份。<br>③ 返回页面后显示 Git 差异、文件摘要和保存状态，未写回 Candidate 的修改不标“已保存”。<br>④ 运行结构、路径、来源摘要及 DSH 配置检查，定位错误文件；真实装载与效果评测另行验证。<br>⑤ 旧实例继续显示原装载快照，提供新 Session 或隔离实例的验证入口。 |
| AG05 能力与模型的实际状态（G1b） | 一个能力写在配置中，不代表实例已加载或用得上；详情页要让人看出问题停在哪一步。 | ① 按 Profile、Preset、模型、MCP、Skill、Plugin 展示来源及“已声明、已装载、已调用”的分层状态。<br>② 服务端分别读取启动 Profile、Session 所选 Preset/模型、Host 装载状态与 Trace，不把启动配置当运行中模型。<br>③ 模型凭据只显示引用是否可用，缺 Key、Plugin 装载失败和 MCP 调用失败分别呈现。 |
| AG06 新建智能体（G1b） | 从空态或列表发起创建后，用户能看到真实创建进度和新增的研究资产，而不是一个只有名称的空卡片。 | ① 前端收集唯一 ID、用途和目标 Experiment，展示将产生的文件与来源。<br>② 服务端校验 ID，调用受控创建服务并返回操作编号、Git 差异和登记结果；双击不重复创建。<br>③ 失败时不留下假 Agent，也不自动启动容器或编造评测结论。 |
| AG07 从已有资产导入（G1b） | 导入旧 Agent 或外部包时，先让用户知道里面有什么、将写到哪里，避免把不明脚本或整个 DSH_HOME 当 Harness 迁入。 | ① 对目录/归档做只读清点，展示来源、可执行内容、依赖和兼容疑点。<br>② 用户选择文件与目标 Experiment 后预览 Candidate 差异，再调用受控导入服务。<br>③ 保留源文件原貌；同名冲突、部分失败和未登记完成均给可核对回执。 |

## 3. 页面：与管理智能体对话，执行平台管理工作

管理对话是首页首选入口。它由专用 DSH 管理 Agent 承载，能理解请求、查询证据、提出修改并调用与页面按钮相同的确定性服务；工具回执决定操作结果。管理会话与业务 Agent 会话分开，管理 Agent 自身的 Profile、Preset、模型和工具版本也应能追溯。

![](/home/admin/Downloads/03_管理对话.png)

顶部固定管理目标；对话区依次呈现计划、变更及影响预览、确认卡和可追溯的操作回执。

| 任务名称 | 任务描述 | 任务内容 |
| --- | --- | --- |
| MG01 专用管理对话入口（G1a） | 用户可用自然语言开始管理任务，同时知道自己正在和“平台管理智能体”说话，避免管理记录混进客户业务会话。 | ① 前端在首页提供管理对话、会话历史和页面深链。<br>② 给管理 DSH 建独立 Profile/Preset/Session，记录当次模型、Skill、Plugin 与工具装载摘要。<br>③ 管理消息只关联管理任务，不写入业务 Agent Session 或业务反馈。 |
| MG02 精确目标与多轮上下文（G1a） | 说“重启它”或“改这个 Agent”时，助手先选定唯一对象；多轮中换目标要重新核对，避免旧计划打到新对象。 | ① 输入框支持点选 Agent、实例、Trace、Run、版本等精确引用，显示 ID、来源和状态。<br>② 服务端持久保存 management_task_id、已确认目标、来源摘要与计划版本；多个候选时继续澄清。<br>③ 切换目标或来源变化时废弃旧预览，不能沿用先前确认。 |
| MG03 查询现状与解释失败（G1a） | 问“现在跑的是什么”“这轮为什么失败”，助手给能点开的原始事实和观察时间；没有证据时说未知。 | ① 为管理 DSH 提供授权的 Agent/实例/Session/Trace 只读工具。<br>② 回答卡区分配置声明、容器观察、实际工具事件和推断，并链接原页面。<br>③ Trace 缺失、观测过期或调用失败时展示缺口，不编造原因。 |
| MG04 管理任务的预览、确认与回执（G1a） | 用户提出复杂管理要求后，先看懂管理助手准备执行的动作和影响；确认后持续看到真实结果，断线也能查回原操作。 | ① 管理 Agent 将请求整理为查询、草稿或执行计划，列出目标、步骤、所需信息和停止条件。<br>② 服务端使用参数与结果明确的统一接口（typed API）预览文件差异或实例、会话影响；“看看能否重启”只预览。<br>③ 确认卡展示精确目标 ID、动作、来源摘要和影响；目标或来源变化时重新预览，不沿用旧确认。<br>④ 页面按钮与管理 Agent 调用同一受控服务，以幂等键创建持久 operation ID，展示受理、运行、完成、失败、未知状态。<br>⑤ 管理任务关联全部子操作；刷新或重连后读取原回执，结果不明先核对实际状态再决定重试。 |
| MG05 通过对话管理实例（G1a） | 说“创建、启动、停止、重启这个实例”，对话展示和实例页相同的预览与真实 Docker/DSH 结果。 | ① 调用实例页的来源、镜像、卷和活跃会话影响预览。<br>② 确认后通过受控服务调用窄执行器，管理 Agent 不直接持有 Docker Socket 或凭据。<br>③ 显示装载快照、实际状态、日志入口及未知结果；重启不能暗中换资产。 |
| MG06 通过对话新建或导入 Agent（G1b） | 用户说出用途和来源，助手可引导完成创建或旧资产导入，并把实际生成的 Agent 交回首页核查。 | ① 复用 AG06 的新建预览和 AG07 的只读清点。<br>② 询问缺失的 ID、目标 Experiment 或文件选择后，调用同一受控服务。<br>③ 将创建回执、Git 差异及 Agent 详情链接放回对话；不执行未确认的归档代码。 |
| MG07 通过对话修改 Harness 与配置（G1b） | “改提示词、换模型、调 Preset”会产生可阅读的 Candidate 差异，并说清哪些是资产变化、哪些只是当前 Session 设置。 | ① 管理 Agent 先定位 Trace/需求和目标 Candidate，提出精确文件改动或模型配置草稿。<br>② 确定性编辑服务预览并在确认后写入目标 Candidate，防止旧 diff 覆盖新修改。<br>③ 显示 Git 回执与新 Session/实例验证入口；不直接把运行 HOME 当资产事实源，也不回显密钥。 |
| MG08 通过对话选择、组合和验证 Hub 能力（G1b） | “给它加 MCP、Skill、Plugin 或知识”时，助手能列具体来源并验证是否真的用上；用户也能让它准备一个组合 MCP 工具流程草稿。 | ① 从四类 Hub 的目录选择唯一资源，必要时澄清同名版本和依赖。<br>② 对“把这些 MCP 工具合成一步”的要求，助手提出 MCP04 的流程、字段映射与预计调用清单，交用户在 Hub 中预览和试跑；未确认不发布。<br>③ 复用 Hub 的发布与 Candidate 绑定服务，展示版本、差异和受影响实例。<br>④ 调用隔离实例验证，区分“已登记、已装载、已调用、评测有益”，返回 Trace 或检索引用。 |
| MG09 通过对话评估与优化（G1b） | 用户可从一次差评出发，让助手提出修改、用同一批 Case 比较，再看到改善和退步；最终研究决定仍由人作出。 | ① 管理 Agent 读取原 Trace、支持例、反例和固定评测口径，给出 Candidate 修改建议。<br>② 调用异步评测服务，分别显示 Baseline 与 Candidate 的 Run ID、逐例结果、资源数据和失败状态。<br>③ 形成引用证据的 Decision 草稿；评分标准变更需重跑，助手不自行写 `adopt`。 |
| MG10 通过对话发布 Harness（G1b） | “发布这份 Harness”会生成一个可恢复、不可变的版本供以后派生变体；发布后不会自动接业务流量。 | ① 读取 Candidate 来源、版本草稿、文件摘要、依赖及真实装载验证结果。<br>② 调用版本页的受控发布 API，在操作者明确确认后保存 `published` HarnessVersion 与操作回执。<br>③ 缺文件、来源漂移或验证失败时保持未发布；Research Decision 与 Research Release 不自动等于平台发布。 |
| MG11 通过对话创建算力变体（G1b） | “基于已发布版做低算力变体”先让用户选准确的父版本，再逐步填写任务、预算和等价标准。 | ① 复用变体页的同 Agent、已发布且可恢复版本选择器。<br>② 引导定义适用任务、模型/工具预算和事前质量与资源门槛，生成独立 Candidate 差异。<br>③ 对话读回同 Case 的 Run 与反例；源版缺失或未发布时只提供发布入口，不从 Git HEAD 偷换来源。 |
| MG12 管理智能体自身资产与回归评估（G1b） | 管理助手也可能选错 Agent、编造引用或误报操作成功，因此它的 Harness 变化需要和业务智能体一样留版本、跑回归。 | ① 固定管理端 Profile、Preset、模型、Skill、Plugin 和受控工具版本，并把建议/工具调用关联管理 Trace。<br>② 建立少量真实场景，覆盖错目标、假引用、漏反例、错误回执与越界写入；变更管理 Harness 后按同一口径复测。<br>③ 页面标明管理助手给出的事实、推断和缺口；凭据值不进其上下文。 |
| MG13 通过对话启用与回退（G2） | 长期业务阶段，操作者可说“启用新版”或“回退”，但要先看到新会话、旧会话和定时任务的影响。 | ① 对话调用部署页的预览、预检、真实探针和路由 API，并按已认证操作者授权。<br>② 操作者确认后仅改变后续新 Session 的默认或可手选版本，旧 Session 保留原装载。<br>③ 显示实际切版/回退回执；普通业务用户、未发布版和未验证版不能经提示词绕过限制。 |

## 4. 页面：MCP、Skill、Plugin 与知识库 Hub

四类 Hub 是平台新建的能力目录和管理入口，不等于锁定版 DSH 已有统一市场。卡片应区分“来源已登记、已绑到 Candidate、实例已装载、调用成功、评测有益”。绑定配置仍写入 Git Candidate；Hub 索引保存来源、关系和观察结果。知识原文保存在其来源或受控上传存储，索引可重建。

MCP Hub 还支持**MCP 工具编排组合**：例如按“查订单→查物流→合并状态”的流程生成一个“查询履约状态”工具，Agent 只需选择一次组合工具，平台在内部继续调用原有工具。组合流程的可编辑定义在 Hub 的受控来源中维护；发布后形成不可变版本，Agent Candidate 只保存绑定引用；Hub 发布组合工具与版本页发布 Agent 的 HarnessVersion 是两次不同动作。锁定版 DSH 的 MCP 客户端负责连接和调用外部工具，编排执行及对外发布新工具需由平台建设；[MCP Tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)提供新工具的发现与调用接口；[授权规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)约束跨服务调用身份。能否节省模型推理、耗时和费用，要通过同任务对照测量。

| 任务名称 | 任务描述 | 任务内容 |
| --- | --- | --- |
| HB01 四类能力目录与使用关系（G1b） | 从 Agent 详情或导航进入 Hub，能分别浏览 MCP、Skill、Plugin、知识库，并看清某个能力被哪些 Agent 使用。 | ① 前端提供四类入口、搜索、空态和来源/版本/最近核验时间。<br>② 服务端只索引 Git、外部来源与 DSH 实际观察，建立能力、Candidate、装载快照和实例的关系。<br>③ 卡片分层显示登记、配置、装载、调用、评测状态；旧观察标过期。 |
| HB02 统一绑定、停用与影响预览（G1b；多人归属 G2） | 页面和管理对话对同一能力进行添加或停用时，生成同一份 Candidate 差异；旧实例不会因改了候选而被误称已卸载。 | ① 选择精确 Agent、Experiment Candidate 和能力版本，展示将修改的文件及依赖。<br>② 通过页面与对话共用的受控接口写入，检查目标摘要和冲突，保存操作回执。<br>③ 解除绑定前列仍在使用的 Agent、Session、实例；多人阶段在所有列表、详情和写入接口校验服务端确认的用户身份。 |

| MCP02 MCP 连接、工具和资源试验（G1b） | 用户可从服务卡分别验证“连得上”“能调用工具”“能读资源”，知道故障发生在哪一步。 | ① 隔离 DSH 实例按锁定客户端支持的协议完成握手或发现与鉴权，记录实际协商版本。<br>② 为选定工具做一次真实 `tools/call`，为资源做一次带 URI 的读取，关联原始错误与 Trace。<br>③ 外部副作用超时先对账；连接成功、工具成功和业务效果用不同状态呈现。 |

## 5. 页面：从已发布 Harness 创建不同算力变体

用户先选某个 Agent **已发布、不可变、可恢复**的 HarnessVersion，再创建该 Agent 的独立变体实验。Git 提交、Research Release、正在编辑的 Candidate 或“当前正在运行”都不能直接充当父版本。发布版本与业务启用是两次不同决定：未启用的已发布版也能派生变体，创建变体不会改变业务流量。

“效果几乎等价”需要质量和资源两类事前门槛：最低可用质量、关键 Case 不退步、相对父版本允许的差额，以及成本/延迟/资源目标。`no-compute` 若使用，严格表示本地和远端模型都不调用，包括工具背后的模型和 embedding；仅不用本地 GPU 不算。无/低/中/完整算力只是可选标签，不预建固定四档。同一次父版与变体比较默认使用父 HarnessVersion 发布时锁定的同一标准 DSH Runtime 镜像，差异留在 Harness 候选与 Run 中；若改用升级后的标准镜像，应另做迁移比较并重新验证，不能称为父版原样运行。

| PV01 版本目录与状态（G1b） | Agent 详情页清楚区分草稿、已发布、已撤回及当前业务启用的版本，用户不会把一个 Git 提交误认成已发布产品版本。 | ① 前端按 Agent 展示 version ID、状态、来源、发布时间、摘要和当前使用情况。<br>② 后端只从平台版本记录读取 `published`，原始 Git 或 Research Release 显示为来源。<br>③ 草稿、撤回与业务启用标识分开展示，未发布时明确说明无法从其创建算力变体。 |
| PV02 发布不可变的 HarnessVersion（G1b） | 操作者把同一 Agent 的候选 Harness 从“可编辑方案”变成“可恢复的已发布版”；发布要经过来源、内容和真实任务核查，成功后仍不会自动接业务流量。 | ① 选择 Candidate，汇集 Git 来源、Experiment、Run、Decision、适用任务和限制；核对同 Agent 身份、内容可恢复性及相关 DSH 运行证据，缺项只留草稿。<br>② 固定文件与逐项摘要、Git 来源、标准 DSH 镜像、Profile/Preset、实际 provider/model/推理参数，以及 Plugin、Skill、外部及组合 MCP、知识绑定的精确内容或摘要；组合流程、编排执行器版本、子工具服务实现的可验证来源/版本和字段指纹也随清单固定，凭据只保留非秘密引用。<br>③ 外部包与知识原文必须能按摘要重新取得，必要时保留受控不可变副本；仅有 URL、包版本或检索索引不足以证明可恢复；外部 MCP 服务实现无法固定或行为漂移时标明复现限制并重新验证，不把字段指纹当行为保证。<br>④ 从清单重建隔离 DSH 实例，核对真实装载，运行相关业务任务并保存 Trace；容器 healthy 或 HTTP 成功不能代替业务通过。<br>⑤ 有权操作者查看证据后显式确认，再原子保存 `published` 状态、操作者、时间、摘要和回执；相同版本 ID 不得对应不同内容，发布不改变业务路由。<br>⑥ 草稿、验证、发布使用可恢复且防重复的操作编号；中断或结果未知时先对账，不留下半个 `published` 版本，也不把受理当成功。 |
| PV03 已发布版本的派生谱系（G1b） | 查看一个新变体时，可以追到同一智能体的已发布父版本、改动实验和评测结果，便于解释它从何而来。 | ① 在新 HarnessVersion 清单记录父版本 ID、摘要、Experiment 与 Run。<br>② 版本详情只读展示父子关系和可恢复性状态。<br>③ 父版本被撤回或实物缺失时仍保留历史关系，但拒绝再次从它派生。 |
| PV04 撤回有问题的已发布版（G1b；业务影响处置 G2） | 一个已发布版发现问题时，可以停止它继续作为新变体的来源，同时保留历史运行和决定。 | ① 操作者记录撤回原因、影响范围和回执；先阻止新变体派生，清单与既有 Run 保持可读。<br>② 若该版仍是业务默认版或手选版，先完成后续新会话路由切换/停用及旧 Session、任务影响处置；无法完成时保留“待撤回”状态，不提前改为已撤回。<br>③ 路由不再接新会话后才标已撤回，旧 Session 与任务按已记录的来源继续处理，不通过删除文件掩盖历史。 |
| VR01 部署页区分默认版与可手选版（G2） | 业务用户可以知道新会话默认进入哪个版本、还有哪些经过验证的版本可手动选择；“已发布”本身不等于“可接业务流量”。 | ① 未来的 Deployment 从单一期望版本扩为“默认版本 + 经确认的可手选版本集合”，读取目标实例的声明与实际装载证据。<br>② 分别展示默认版、可手选版及适用 Target；手选只发生在新 Session 建立前，不按流量权重自动分配。<br>③ 未发布或未完成业务启用验证的版本不可进入业务入口。 |
| VR02 启用版本：影响预览、预检与确认（G2） | 长期业务使用前，操作者能看清切版会影响哪些新旧会话和任务，看到目标版的真实任务证据，确认后查得到可靠的启用操作结果。 | ① 预览目标实例、新会话路由、活跃 Session、Schedule、在途任务和回退目标；逐项决定旧任务继续、停止或经验证迁移，未知归属明确标出。<br>② 核查镜像、资产摘要、Profile/Plugin 兼容、能力装载和凭据引用，在目标隔离实例执行真实模型或工具任务，保存 Session/Trace。<br>③ 页面分别标明“配置声明、运行已观察、业务已验证”；缺镜像、能力或业务任务失败时不进入切版。<br>④ 有权操作者确认精确源/目标版本、影响和证据；来源或任务状态变化使预览失效并要求重算，研究决定和 AI 建议不能代为确认。<br>⑤ 使用持久且防重复的操作编号展示受理、准备、待切换、待实测、失败与未知状态；断线后对账，预检失败保持原路由，只有 VR03 的新会话路由实测通过后才标“启用成功”。 |
| VR03 新会话路由与旧会话粘性（G2） | 启用成功后，普通新会话进入新版；原有会话仍在原版本继续，用户手选版本也必须有清楚的来源。 | ① 原子更新 Deployment 默认版本，对新 Session 固定版本和实例；仅允许显式选择已启用的版本。<br>② 保留旧 Session→旧实例的路由、HOME 和不可编辑装载内容，重启时按清单核验。<br>③ 实际发起新会话并查装载和 Trace；旧资产缺失时报告无法恢复，不悄悄转新版。 |
| VR04 启用后观察与旧实例退役（G2） | 启用并不止于容器正常；页面持续显示真实错误、反馈和旧版剩余会话或任务，帮助判断何时可退役旧实例。 | ① 按版本展示新会话成功与错误、延迟、Trace、用户反馈及与预期的偏差。<br>② 汇总旧 Session/任务剩余数和处理回执，在途或归属未知时不标“可清理”。<br>③ Runtime 或 Plugin 版本升级需重新核兼容与会话恢复；旧实例仍有依赖时保留旧镜像和装载。 |
| VR05 业务版本回退（G2） | 当新版效果不佳时，操作者能把后续新会话切回已验证旧版；旧回答、在途任务和外部副作用仍有清楚说明。 | ① 回退前预览目标、新会话、旧会话和 Schedule 的去向，并说明已产生结果不能撤销。<br>② 经有权操作者确认，保存可追踪操作回执，失败时保持原路由。<br>③ 实际发起新会话验证进入旧版和目标实例，旧会话仍按原版继续。 |
| VR06 手选版本的加入与停用（G2） | 操作者可以允许另一个已发布变体供新会话手动选择，也可以停止新的手选；这两种操作都不改变默认版。 | ① 加入可手选集合前复用镜像/资产预检、真实业务探针、影响预览和显式确认。<br>② 停用前列出使用该版的 Session 与 Schedule，只移除后续新会话入口。<br>③ 旧会话和任务保持来源，历史启用与停用回执可查。 |

## 12. 页面：用户、运行设置与运维恢复

本页以“设置”和“运维”两个页签展示当前真正生效的版本、连接状态、故障、备份与恢复范围。只有平台开始服务独立业务用户时，才建设 G2 身份和用户数据隔离；这些设计不反向成为当前个人 Research Mode 的基础设施。

![](/home/admin/Downloads/11_设置与运维.png)

“设置”展示版本和能力的实际状态，“运维”提供日志、备份恢复与数据保留；用户隔离和容量入口随 G2/G3 建设。

| 任务名称 | 任务描述 | 任务内容 |
| --- | --- | --- |
| OP01 平台版本与能力状态（G1a） | 操作者一眼看见平台、DSH、镜像、模型和外部能力实际处于什么状态，避免用旧配置或一个连接成功的提示判断可用。 | ① 页面并列显示版本锁、实际镜像、服务和 Plugin 版本及最近核验时间。<br>② 展示各实例模型、MCP、Plugin 的配置、连接、激活和业务调用证据。<br>③ 版本漂移或只有 endpoint/initialize 成功时标明尚未完成业务验证。 |
| OP02 分层健康、日志与故障定位（G1a） | 从失败按钮可以一路找到平台操作、执行器和 DSH 的具体错误，而不是只看一个“服务正常”的灯。 | ① 分别监测平台 API、容器执行器、DSH 实例和事件采集器。<br>② 日志按 operation、instance、request、Session 或 Trace 关联，保留原始错误码与观测时间。<br>③ 页面区分受理、完成、失败和未知，日志与模型上下文均不输出凭据值。 |
| OP03 备份范围与执行（G1a） | 点备份前，操作者知道 Git Harness、平台状态、实例 HOME、原始 Session 和附件各在哪里；备份后得到可核对的时间与结果。 | ① 按事实源列备份范围、目标卷、摘要与恢复点，不把整个 `DSH_HOME` 写成 HarnessVersion。<br>② 对选定实例数据和平台映射做一致性备份，保存 operation 回执。<br>③ 失败时标失败和未覆盖部分，不以“文件存在”冒充已可恢复。 |

| OP05 数据位置、保留和删除回执（G1a；删除 G2） | 页面明确区分运行会话、Trace 索引、研究 Run、测试题各自的存放和保留方式；删除时不会把“删了索引”说成“删了源数据”。 | ① 显示数据来源、保存地点、保留时间及清理影响。<br>② 对 Session、附件、索引分别执行删除和记录结果，运行中的请求与失败项单独显示。<br>③ 不改写不可变 Run；需要删除或限制访问的事实按对象逐项处理并留回执。 |

| OP07 同 Agent 多用户数据隔离（G2） | 两个人使用同一个业务 Agent 时，彼此的对话、附件、定时任务和历史不能串到一起。 | ① Session、附件、Schedule 及执行历史的读取、修改、删除和后台触发都按服务端 actor 归属检查。<br>② 以双用户测试从 UI、Remote/API 和模型工具交叉访问、改删及到期投递。<br>③ 任一入口越权时不开放共享 Host，页面展示失败范围和处置结论。 |
| OP08 隔离失败后的独立 Host 与恢复路由（G2） | 若共享 DSH Host 无法可靠隔离用户，平台仍能用按用户分开的 Host 和卷提供同一 Agent，并在重登或重启后找到原会话。 | ① 复用同一 Agent 标准镜像与只读 Harness，为不同用户分配独立 Host/HOME。<br>② 持久保存 actor→Host/卷映射，业务入口按已认证身份路由并在重启或恢复时对账。<br>③ 映射未知时拒绝请求，不能临时建立假空会话掩盖丢失。 |
| OP09 凭据更新与泄露边界（G2） | 操作者知道某次模型或 MCP 凭据更新影响哪些实例、何时生效；普通页面、日志、Run 和管理智能体都看不到密钥值。 | ① 使用专用凭据来源和引用，显示受影响实例、重载进度与失败回执。<br>② 运行时注入并检查日志、Trace、Run、AI 工具输入不含密钥值。<br>③ LLM API Key 保持本地忽略文件边界，版本清单只保存非秘密引用。 |
| OP10 事故告警与处置演练（G2） | 平台长期运行后，故障告警能直达对应实例和 Trace；值守者照页面说明就能完成停止、恢复或回退。 | ① 对真实错误率、延迟、不可用和差评设置少量有负责人承接的阈值，告警链接原始证据。<br>② 为当前部署写清检查、停止、恢复和回退步骤及实际命令。<br>③ 让非原作者按说明演练一次，记录无法执行或实际结果不符的步骤。 |
