# DSH 智能体运行管理平台设计方案

> 状态：未来独立工程或明确的新项目阶段的设计方案，尚未实现。本文不改变本仓库的 Research Mode，不要求迁移现有 Python/Shell 工具，也不构成本仓库的生产验收标准。当前边界以 [项目解释](standards/PROJECT-INTERPRETATION.md) 和 [项目验收矩阵](ai-agent-harness项目验收矩阵.md) 为准。

## 目标与取舍

平台要解决的不是“再运行一个 Agent”，而是持续管理一组相互独立、以容器运行的 DSH Agent：知道每个实例实际装载了什么 Harness，允许比较改进前后的行为，并能在有证据、有人确认的条件下发布和回滚。由此倒推，最小的闭环是：**可定位的运行事实 → 可复现的候选与评估 → 有记录的发布决定 → 可观测、可回退的运行版本**。缺少其中任一环，智能化建议都不能直接变成生产变更。

平台自身也运行在特化的 DSH Runtime 中。管理界面提供确定性操作；同一 Runtime 中的管理智能体理解自然语言，并调用平台服务完成诊断、方案生成、实验编排与结果解释。两种入口读取同一事实、遵守同一服务端规则；不是在传统管理后台外接一个聊天框。DSH 的 [Cordis 插件与 Profile 组合机制](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) 是首选扩展点。

首版约束：单机 Docker、单组织多用户、统一业务流量入口；只设 `member` 与 `publisher` 两类角色。`member` 可以管理草案和运行评估，`publisher` 可以确认发布、灰度调整与回滚，也允许确认自己的变更；所有决定记录操作者与依据，不建设双人审批流。暂不做租户体系、Kubernetes 调度、通用策略引擎、任意第三方插件自动安装或自主生产发布。规模或合规要求出现真实瓶颈后，再评估这些能力。

## 技术形态与开发语言

```text
管理用户 / 管理智能体 ── UI、Remote API ──┐
业务调用方 ────────── 统一业务流量入口 ───┤
                                        ▼
                              平台 DSH Runtime（特化 Profile）
                              ├─ Agent 注册、版本、能力目录插件
                              ├─ 实验评估、资产、发布审计插件
                              ├─ 会话网关、平台状态库与证据索引
                              └─ 受限调用 ── 独立容器执行器 ── Docker Engine
                                                              ├─ DSH Agent A 实例
                                                              └─ DSH Agent B 实例
```

平台 Host、管理插件、业务入口适配器、容器执行器及 Web 客户端等**平台自有应用代码统一使用 TypeScript/TSX**；服务端运行在 Node.js，Web 客户端运行在浏览器。理由是 DSH 的[源码构建配置](https://github.com/deepseek-ai/deepseek-harness/blob/master/package.json)和插件、Client/Host 约定均以 TypeScript 为主；同语言可以直接复用其服务类型、事件、Profile 与 [Remote API](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/api-gateway.zh.md)，减少跨语言协议和维护成本。这是未来平台的选型，不是“所有文件都改成 TypeScript”：Harness 文档与配置仍可用 Markdown/YAML，数据库模式仍用 SQL，Docker/Compose 配置保留原格式，第三方 MCP Server 或 Skill 源码不强制改写，本仓库的研究 CLI 也不迁移。具体 Node.js 版本随选定的 DSH 发行版锁定，不在此另立一套运行时。

平台通过新的 DSH Profile 装配插件，不复制或改写 Agent loop。只有插件扩展点确实不足，并经最小原型验证后，才修改 DSH 上游接口；修改必须能回退且不改变普通 DSH Profile 的默认行为。Web 界面扩展 DSH Client，管理操作使用同一 Host 服务暴露的 Remote 方法；流式会话仍按 DSH 的会话/流协议处理，不能把一元 `@Remote` 方法误当成跨容器流协议。

每个业务 Agent 是独立 DSH 容器，拥有自己的 Profile、只读 Harness 装载、运行配置、凭据注入和持久化运行卷。平台只记录并控制期望版本及实例状态，不把 `$DSH_HOME`、Session 或缓存打包成 Harness；需版本管理的平台和实例凭据保存在 Agent 的实例专用路径。独立容器执行器是唯一接触 Docker Socket 的窄接口，平台智能体不能直接调用 Docker，也不得接收凭据值到模型上下文；执行器仅接受服务端授权的创建、查询、停止和替换指令。

平台的统一网关负责外部身份、Agent 选择、版本路由、流转发和会话粘性。它不把各业务容器的 Web 端口直接暴露给用户。现有 DSH Web 的 [浏览器启动令牌和 cookie](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/client/connection/README.zh.md)主要是单进程 owner 访问边界，不等同于多用户身份与跨容器 Agent API。首个技术原型须验证受支持的会话入口；若不足，则在业务 DSH 容器中增加最小私有入口插件，由网关通过受限的容器间通道调用，而不复用浏览器令牌充当服务凭据。平台侧也需增加多用户认证和身份传递，所有管理方法在服务端校验角色与对象范围。

## 核心对象与事实来源

| 对象 | 含义与唯一事实来源 |
| --- | --- |
| `Agent` | 稳定业务身份、用途和关联的 Harness 源码位置；平台状态库维护注册信息。 |
| `HarnessVersion` | 不可变装载清单：Git 来源、资产摘要、DSH 镜像、Profile/能力版本、模型路由标识及非秘密运行配置；由构建产物清单确认实际内容。 |
| `Experiment` | 一个改进假设、固定比较口径、Baseline/Candidate 引用、评估运行与结论；候选源码仍在 Git 工作树，不复制多份可编辑基线。 |
| `Deployment` | 某 Agent 期望运行的已发布版本、流量权重及回滚目标；平台状态库维护期望状态和决定记录。 |
| `Instance` | 一个实际 DSH 容器及其健康、装载摘要、容器/卷标识；观测状态来自 Docker 和 DSH 装载检查，不用期望状态冒充实际状态。 |
| `Session` 与证据资产 | Session 原始记录留在实例运行存储；平台索引其来源、失败样本、反馈、Trace 关联、评估结论和必要的脱敏片段。 |

表中的 `Agent` 是平台登记的长期业务身份，不等同于 DSH 进程内某次会话的 Agent 对象。

这里的“能力市场”首版是一个可审核的 MCP/Skill 版本目录：展示来源、版本、依赖、权限需求及适用 Agent，选择后只写入 Candidate Harness 的能力清单。安装或升级通过新实例验证，不对生产实例热改，不自动执行不可信仓库内容。市场是资产发现与选型入口，不是新的任意代码执行通道。

单机阶段用一个事务型平台状态库保存注册、期望状态、身份角色、实验索引、发布/回滚决定和审计事件；优先评估 SQLite，确认并发写入与备份需求后再决定是否换库。Git 是 Harness 源码和可版本管理实例凭据文件的事实源；本地忽略文件是 LLM API Key 的来源，不可变发布包以内容摘要标识，运行卷是 Session 事实源。索引允许重建，但原始运行事实和发布决定不能静默覆盖。DSH 的 [会话遥测](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session-telemetry.zh.md)可用于诊断，不把可选遥测投递当作可靠审计或完整评估证据。入库前按需要脱敏；平台和实例密码及非 LLM API 凭据可按任务需要纳入 Git，LLM API Key 只保存在被 Git 忽略的 `*.llm-api-key` 文件中并在运行时注入。任何凭据都不进入模型上下文、普通 Trace、评估样本或发布包。

## AI 原生的受控演进闭环

1. **发现与分析**：从 Session、失败样本、用户反馈和线上指标建立带来源的证据资产。平台智能体可聚合问题、复现失败、提出能力缺口和候选方案；结论必须标明证据与未知项，不能把模型推断写成运行事实。
2. **候选改进**：智能体或用户在隔离的 Experiment 工作树修改 Prompt、Preset、Skill、MCP 配置等 Harness 资产。配置变更也形成新版本，不在运行容器中直接修改生产配置。评估记录 Candidate 的 Git 提交、dirty 状态和装载摘要；发布前须固定为可重建的已提交来源，内容改变则重评。
3. **评估解释**：Baseline 与 Candidate 分别在隔离 DSH 实例运行，使用事先确定的输入、模型条件、判断口径和回归点。记录实际装载、输出、失败、成本/时延与限制；口径变了就重跑受影响比较。管理智能体可以解释结果和建议下一步，但不能把静态检查或容器健康当作行为改进证明。失败或证据不足时结论为拒绝/继续研究，不进入发布。
4. **发布确认**：通过评估的 Candidate 打包为不可变 `HarnessVersion`。`publisher` 查看差异、评估与影响范围后显式确认；同一人可以自确认，但服务器必须记录身份、版本摘要、依据和时间。管理智能体可准备发布说明，不能自行完成确认；任何入口都不能绕过服务端门禁。
5. **灰度与回滚**：先把少量**新 Session** 路由到候选版本，已有 Session 固定在原版本；按健康和业务指标人工扩大流量。异常时停止新流量并恢复旧版本，记录触发原因和结果。旧实例在其 Session 排空前保留；不能恢复的 Session 明示失败，不承诺透明迁移。灰度或回滚后继续收集证据，进入下一轮 Experiment。

发布门禁不要求统一的固定 Case 数或“分数过线”模板；每个 Agent 的评估合同应在比较前写明关键行为、回归风险及不可接受的失败。必要的确定性规则——版本不可变、评估引用一致、身份授权、显式确认、审计落盘、健康检查和路由一致性——由平台服务端执行，不能交给大模型自行判断。自动动作首版只限于阻止新版本继续接收流量等预授权的保护行为；是否正式回滚和如何处置已有 Session 仍需有记录的操作决策。

## 首个可交付切片与验证

先做一条端到端纵切，不先建设完整“市场”和通用工作流：注册两个不同 Agent，分别启动独立 DSH 容器；为其中一个 Agent 建立 Baseline/Candidate、评估、人工发布确认、少量新会话灰度及回滚；再接入管理智能体，要求它能用同一批服务和证据解释一次失败并生成候选建议。界面至少能直接完成注册、查看实例、查看评估与发布/回滚；自然语言入口负责跨模块分析，不替代确定性按钮。

该切片的验收看实际行为，而非仅看配置文件或 HTTP 健康：两个 Agent 的容器、运行卷和装载摘要相互独立；Baseline/Candidate 的实际用户可见结果可比较；发布前不改变生产版本；灰度只影响新 Session，旧 Session 保持绑定；失败评估和无权用户无法发布；重启后期望状态与实际实例可对账；回滚后新 Session 确实回到旧版本，原始证据和操作记录仍可追溯。还须实际验证跨容器会话协议、多用户身份传递、流转发和实例重建后的 Session 行为；这些目前是设计待验证项，不能因文档完成而宣称可用。

若上述纵切不能证明重复评估与发布决策确有管理成本，暂停扩展平台范围，继续使用本仓库的轻量 Research Mode。未来平台即使落地，也应把这里已有的 Experiment/Research Release 当作研究输入；Research Release 不是生产发布批准，两者的生命周期和验收记录不互相替代。
